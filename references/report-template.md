# 报告模板：漏洞报告与任务收尾

> ARTEX reporter 提示词的单文件版。出报告/收尾时读。

## 一、severity 判定标准

| 等级 | 标准 |
|---|---|
| critical | 直接获取系统控制权/RCE/核心数据库整库拖走/认证全面绕过 |
| high | 敏感数据大量泄露、任意文件读写、越权到管理员、存储型 XSS 打管理员 |
| medium | 需要条件的漏洞：反射 XSS、有限越权、逻辑漏洞（可利用但影响面窄） |
| low | 信息泄露、低危害配置问题、理论可利用但门槛极高 |

拿不准就就低不就高，并在报告里写明判定理由。

## 二、单漏洞报告模板（findings/NNN-slug.md）

```markdown
# [F-NNN] <漏洞标题：资产+漏洞类型+一句话影响>

- severity: high
- vulnclass: idor / sqli / xss / rce / auth-bypass / info-leak / logic / …
- asset: https://api.example.com （service #S03 → endpoint #E17）
- status: confirmed
- 发现意图: #intent-03
- 日期: 2026-10-10

## 概述
一段话说清：什么资产的什么功能存在什么问题，攻击者能借此得到什么。

## 影响与危害
具体化：能读到什么数据/执行什么操作/横向影响到哪些资产。不写"危害巨大"这种空话。

## 受影响范围
- 精确 URL / 接口 / 参数
- 哪些账号/角色受影响

## 复现步骤（可照做）
1. 前置条件（测试账号/环境状态）
2. 完整 curl/操作序列，逐条对应预期输出
3. （代码型漏洞附最小触发 payload）

## 证据
- ev-012-a3f8c2d1.txt：原始请求+响应全文
- ev-013-9b1d0e77.txt：独立复现（换会话）记录
（贴关键片段原文，不转述、不裁剪关键行）

## PoC
完整可运行的脚本/命令块。

## 根因分析
为什么存在这个漏洞（鉴权缺失/过滤不严/…），尽量定位到代码或配置层面。

## 修复建议
面向开发者：具体怎么改（校验什么/过滤什么/加什么鉴权），优先给短期止血+
长期根治两条。
```

## 三、任务收尾总结模板

```markdown
# 任务收尾：<任务名>（<日期>）

## 授权与范围
scope 摘要 + 是否全程合规（含 out-of-scope 误触说明，若有）

## 达成项
- 目标逐条对照：达成/未达成 + 依据（指向 facts）

## 确认漏洞
| # | 标题 | severity | 状态 | 报告文件 |
（confirmed 全列；inferred 高价值嫌疑列在后面并标注"待验证"）

## 进行中/未走完的路线
每条：路线 → 已走到哪一步 → 卡点 → 恢复条件

## 封锁方向
每条：方向 → 试过什么 → 卡在哪 → 何种新机理可重开

## 账本统计
资产 X 条（已测 Y）/ 事实 Z 条（observed A / inferred B）/ 证据文件 N 个

## 建议后续动作
下一步最值得做的 1-3 件事
```

## 四、报告纪律（ARTEX reporter 原文要点）

- **每条陈述有证据支撑**，绝不臆造请求响应；记不清就重查 evidence，禁止脑补。
- 面向修复写：根因和修复建议是给开发者看的，不是给领导看的。
- 证据版本对齐：报告引用的 evidence 文件如在报告后更新过，报告头部标注
  "证据已更新于 <日期>，结论待复核"。
- 复测不改历史：新结论新文件，旧报告原样保留（见 evidence-rules.md §4）。
